Streams, Redirection and Pipes

Route standard input/output/error deliberately and build a pipeline without hiding failures.

Revision route: understand the model · work through evidence · practice safely · check recall · review sources.

Core lesson · Streams, Redirection and Pipes
01

How to think about it

Unix processes commonly use file descriptor 0 for standard input, 1 for standard output, and 2 for standard error. Redirection changes where a descriptor reads or writes: `>` replaces a file, `>>` appends, and `2>` redirects errors. A pipe sends one process’s stdout to the next process’s stdin. A pipeline can hide an earlier command’s failure unless its status is handled; Bash `pipefail` makes the pipeline fail if a component fails.

Key facts to remember
  • Use stdout for expected results and stderr for diagnostics.
  • `>` truncates; `>>` appends. Confirm before redirecting to a file that contains useful data.
  • `2>&1` duplicates stderr to the current stdout destination; redirection order matters.
  • `set -o pipefail` helps report a failed command inside a pipeline.

Worked example
02

Follow the evidence

`dosti_tracker.sh list 2>errors.log | sort` sends normal listing output into `sort` while errors go to a separate file. If `list` fails, `pipefail` allows the script to return a failure rather than the successful status of `sort`.

Reasoning sequence
  1. Run a command with normal output and a deliberately invalid option; observe stdout and stderr separately.
  2. Redirect output to a temporary file and inspect it.
  3. Pipe sample records to `sort` or `awk` and explain each stage.
  4. Enable `pipefail` and compare exit status when the first command fails.

Common mistakes
05

Where learners overclaim

Use these corrections to review your notes and lab evidence.

Avoid these shortcuts
  • Redirecting with `>` to an important file and truncating it.
  • Sending diagnostics to stdout where they are mistaken for data.
  • Assuming a pipe automatically preserves every component’s failure status.
